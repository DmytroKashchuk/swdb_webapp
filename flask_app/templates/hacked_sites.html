{% if key == 'victims' %} Domains found on ransomware leak sites, matched to SWDB 2022 sites by URL. A domain is hacked when it is also listed as a victim on ransomware.live. {% else %} US municipalities hit by ransomware, each paired with a comparable non-hacked municipality (match pairs), matched to SWDB 2022 sites by URL. {% endif %} {% if level == 'sites' %}One row per SWDB site whose URL matches a domain.{% elif level == 'domains' %}One row per domain, collapsing every SWDB site it matches.{% else %}One row per domain resolved to a single SWDB account (organisation) via account_url, falling back to site_url; technologies aggregated over all sites of that account.{% endif %} How is this table built?

Logic used to build this table
  1. Source list. {% if key == 'victims' %} Domains extracted from ransomware leak sites (domains_from_ransom_leaks, with the leak Group and First seen). Each domain is looked up in ransomware_live_victims.website (case-insensitive, trimmed): if found, hacked = true and the ransomware.live group, publish date and country are attached; otherwise hacked = false. {% else %} municipalities_matchpairs: each ransomware-hit US municipality (hacked = True) is paired through matchid with a comparable municipality that was not hit (hacked = False). The hacked flag, group, dates, state, population and activity come straight from this table. {% endif %}
    2. {% if level == 'accounts' %}
  2. Normalise domains. On both sides (source list, account_url, site_url) the URL is lower-cased and stripped of scheme, www., path, port and query, so https://www.Example.com/about and example.com compare equal. Source entries that are not a valid hostname (e-mail fragments, file names, empty strings) are discarded; duplicates collapse to one domain with hacked = bool_or.
  3. Resolve each domain to one account.
    • Step A — account_url: all 2022 accounts (all regions) whose normalised URL equals the domain are candidates. Tier 1: a single candidate. Tier 2: several candidates but one holds ≥ 80% of their combined account_nb_sites → it is taken as the parent (e.g. Government of District of Columbia, 397 sites, vs. dozens of one-site accounts that copy dc.gov). Tier 3: no clear parent → the largest candidate is kept but the row is flagged ambiguous.
    • Step B — site_url, only for domains with no account_url hit: the accounts owning sites with that URL are candidates, weighted by the number of matching sites. Tier 4: one owning account (typically a subsidiary brand of a parent with a different URL, e.g. abf.com → ArcBest). Tier 5: one account owns ≥ 80% of the matched sites. Tier 6: ambiguous, largest kept and flagged.
    Step B is never run for domains already resolved in Step A, which is what prevents the fan-out of the site-level view. The result is stored in the database table domain_account_match (source, domain, account_id, matched_on, match_tier, n_candidates, ambiguous) so it can be reused in SQL.
  4. Technologies per account. num_sites and n_technologies (distinct products) are counted over all sites of the account, whatever their site_url. n_controls (distinct security products) comes from all_2022_nist_controls and the has_identify … has_recover flags from all_2022_nist_phases — the same precomputed tables used by the All Regions NIST Categories page; n_nist_phases = phases covered (0–5).
  5. Descriptive columns (group, dates, country, …) come from the source list, aggregated per domain: distinct values joined with commas, dates take the earliest value.
  6. Statistics. Cards and the NIST coverage table are recomputed on the filtered rows, each account counting once. Percentages are shares of accounts; the odds ratio compares hacked vs not-hacked accounts: OR = (a·d) / (b·c) with a = hacked accounts with the category, b = hacked without, c = not hacked with, d = not hacked without. Filter ambiguous = No (tiers 1, 2, 4, 5) for the clean subset.
Caveats: several source domains can resolve to the same account (subsidiaries of one group) — the account then appears once per domain. Domains whose URL is not in SWDB at all are counted in the source summary above but have no row. The 80% parent rule is a heuristic: check n_candidates and match_tier when a match looks odd. {% if key == 'municipalities' %}A domain listed both as hacked and as a control in the match pairs collapses into a single hacked row.{% endif %}
{% else %}
  • Match to SWDB. Every domain is joined to all_2022_sites (all regions) on lower(trim(site_url)) = lower(trim(domain)). A domain can match many sites (branches, subsidiaries or unrelated sites that share the same URL), and every matched site inherits the hacked flag of its domain. Domains with no matching site are counted in the source summary above but have no rows here.
  • Technologies. All technologies installed at the matched sites (all_2022_sites_technology) are joined to universe_installs_enhanced on product_id to get security_product, nist_phase and the security category.
    • {% if level == 'sites' %}
  • Aggregate per site. The technology rows are grouped by site: n_technologies = distinct products installed; n_controls = distinct products flagged as security products; has_identify … has_recover = the site has at least one security product in that NIST phase; products with no phase or phase Multiple set has_uncategorized; n_nist_phases = how many of the 5 phases are covered (0–5).
  • Descriptive columns (group, dates, country, …) are taken from the source list and aggregated per domain: distinct values are joined with commas, dates take the earliest value.
  • Statistics. Cards and the NIST coverage table are recomputed on the filtered rows, each site counting once. Percentages are shares of sites; the odds ratio compares hacked vs not-hacked sites: OR = (a·d) / (b·c) with a = hacked sites with the category, b = hacked without, c = not hacked with, d = not hacked without.
    • Caveats: a large domain (e.g. a hotel chain) contributes thousands of sites that all count as hacked, so it dominates the statistics — filter on domain or total_sites in the domain view to check. Sites are technology-level snapshots: a site with no technology rows does not appear. {% if key == 'municipalities' %}Some domains are listed both as hacked and as a control in the match pairs (e.g. one state domain used by several departments): those sites appear twice, once per flag.{% endif %}
    {% else %}
  • Collapse to one row per domain. Two independent aggregations are joined on the domain:
    • Site totals — first the distinct sites of the domain are listed (one row per site, regardless of how many technologies it has), then summed: total_sites, total_accounts, total_employees, total_ict_spending, total_revenue_usd.
    • Technology totals — over all technology rows of the domain: total_technologies = distinct products across all its sites; total_sec_products = distinct security products; has_identify … has_recover = at least one security product in that phase at any site; total_nist_categories = phases covered (0–5). A product installed at 100 sites counts once.
    hacked is true if any source row of the domain is hacked (bool_or).
  • Descriptive columns (group, dates, country, …) come from the source list, aggregated per domain: distinct values joined with commas, dates take the earliest value.
  • Technology list. Clicking a domain opens its distinct technologies with the number of matched sites where each one is installed (precomputed together with this table).
  • Statistics. Cards and the NIST coverage table are recomputed on the filtered rows, each domain counting once whatever its size. Percentages are shares of domains; the odds ratio compares hacked vs not-hacked domains: OR = (a·d) / (b·c) with a = hacked domains with the category, b = hacked without, c = not hacked with, d = not hacked without.
    • Caveats: totals are sums over every matched site, so a domain shared by many unrelated sites gets inflated employees/revenue and a very long technology list; the “has phase” flags are true if any site has the control, which favours large domains. Use total_sites (e.g. <=5) to focus on domains that map to a single organisation. {% if key == 'municipalities' %}Domains listed both as hacked and as a control in the match pairs collapse into a single hacked row.{% endif %}
